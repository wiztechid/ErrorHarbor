## Day 2 — Capture better evidence

**Subject:** Before you change a setting, write down these four things

When an error appears, the next fix is easier to choose if you first record:

1. The exact error text or command output.
2. The product version, operating system, and environment.
3. What changed shortly before the failure.
4. Whether one person, one device, or the wider system is affected.

Keep sensitive values out of screenshots and shared logs. A redacted error and a clear environment are usually more useful than a long unfiltered dump.

**Try this:** add those four details to the incident note in your field guide. Then find the matching exact-error page in the [Error Library].

— ErrorHarbor

## Day 5 — Protect the recovered state

**Subject:** The repair worked. Can you restore what matters?

After service returns, check the recovery path before you need it again. Confirm what is included in the backup, when the last successful copy ran, how long it is retained, and whether a restore test has succeeded for the system that failed.

Do not buy a backup tool just because an error occurred. Start with your recovery requirement, data scope, restore time, and existing platform options.

If a basic or built-in option is enough for your situation, use that. A paid service is not part of the fix for the original error. ErrorHarbor may add a relevant backup resource after it has verified fit, partner approval, and the referral terms.

— ErrorHarbor

## Day 14 — Close the loop

**Subject:** Turn one solved error into a short runbook

Use this five-line runbook:

- Symptom and exact error
- Product/version and environment
- Safest useful first check
- Escalation evidence to collect
- Verification step and recovery path

This makes the next incident less dependent on guesswork. If a credential, certificate, database, or VM issue was part of your incident, review the relevant recovery and security controls before calling it finished.
