checkDebugAarMetadata Failed: Read the AAR Requirement First

Execution failed for task ':app:checkDebugAarMetadata' names the compatibility check that stopped the build—not usually the root cause. Read the first requirement underneath it. A dependency may require a higher compileSdk, a newer Android Gradle Plugin (AGP), or an SDK extension. Identify that dependency and requirement before changing versions.

🔎 Quick Check — copy the first dependency requirement, not the task name

Under checkDebugAarMetadata, find the first issue that names a dependency and what it requires. Do not copy a version number from a forum before reading your own build output.

Dependency 'group:library:version' requires libraries and applications that depend on it to compile against version X or later of the Android APIs.

Verify: You can name both sides of the mismatch: which dependency requires which minimum build capability, and what your consuming module currently uses.

What checkAarMetadata is actually checking

Android libraries are distributed as AARs. AAR metadata can declare compatibility requirements for consumers, including a minimum compileSdk, minimum AGP version, and minimum compile-SDK extension. Android's documentation describes these fields as build-time requirements intended to fail early with a useful message instead of producing a later ambiguous resource or tooling error.

Fix #2 — dependency requires a higher compileSdk

minCompileSdk is the minimum compileSdk a consuming module can use for that AAR. A library can require it because its manifest or resources use newer platform attributes. Compare the number in your error with the effective compileSdk of the module consuming that dependency.

Do not change minSdk or targetSdk just to satisfy this message. compileSdk controls the Android APIs/resources available while compiling. minSdk is the app's minimum runtime/install API boundary, while targetSdk controls runtime behavior and tested-target semantics. They are different decisions.

Before raising compileSdk, confirm that the required Android platform is installed and that your current AGP supports that compile API level. Newer compile SDK levels can themselves require a newer AGP.

Verify: Rerun the same variant. The original AAR metadata issue for that dependency/minCompileSdk should disappear without unrelated SDK values being changed merely to make the check green.

Fix #3 — dependency requires a newer Android Gradle Plugin

AAR metadata can declare minAgpVersion: the minimum AGP version required to consume the library. If that is the concrete issue, changing compileSdk alone does not satisfy it.

Locate where your project actually declares AGP—such as the plugins DSL/version catalog/build configuration used by the project—and assess the AGP upgrade as a build-toolchain change. Check the project's Gradle/JDK and Android compatibility requirements rather than changing only the plugin number in isolation.

Do not upgrade AGP, Gradle, JDK and every Android SDK number simultaneously unless the supported upgrade path requires it. Preserve the original requirement and make the smallest coherent toolchain change you can verify.

Verify: The build now uses an AGP version that meets the named AAR requirement, and that exact minAgpVersion metadata issue is gone.

Fix #4 — the AAR requires a compile SDK extension

AAR metadata can also declare a minimum compileSdkExtension. Treat that as its own requirement. A higher base API number does not automatically prove the required SDK extension is configured.

Read the exact extension requirement from the error and align the consuming module with the library's documented requirement using a supported AGP/SDK setup. Do not change minSdk as a substitute.

Verify: The consuming module satisfies the named extension requirement and the same metadata issue no longer appears.

Fix #5 — a dependency upgrade introduced the failure

If the build was green before a library update, compare the AAR requirement reported for the new version with your current build stack. You have two legitimate directions: adopt the newer supported build capability, or use a dependency release whose documented requirements match the toolchain you intentionally support.

Do not downgrade randomly until the task passes. Pinning an older library is a compatibility decision: check its security fixes, API behavior and transitive dependencies, and record why the project cannot yet adopt the newer requirement.

Verify: The selected dependency/toolchain combination is intentional and reproducible, and the same AAR metadata check passes on a clean checkout/CI environment—not only one developer machine.

Fix #6 — Flutter, React Native, or multi-module build: change the consuming Android module

The outer framework does not change what the metadata means. Find the Android module/variant named by the failing task and determine where its effective compileSdk, AGP and dependencies come from. In multi-module builds, changing an unrelated module may leave the failing consumer unchanged.

If build properties are centralized, remember that modern Android builds can define common SDK settings at project/settings level while module-level values can override them. Confirm the effective value used by the failing module, not merely the first compileSdk string you find.

Verify: Rerun the same module/variant task and confirm the original dependency requirement is gone.

What not to do

Do not troubleshoot the words checkDebugAarMetadata as if they were the root cause; read the first metadata issue below them.Do not copy a compileSdk number from another developer's error; use the minimum stated by your dependency and a supported toolchain.Do not raise minSdk or targetSdk to satisfy a minCompileSdk requirement.Do not suppress/patch AAR metadata to force an incompatible library through the check.Do not upgrade or downgrade multiple toolchain components blindly; keep the compatibility change explainable.Do not edit generated Gradle/build output as the durable fix.

Only seeing the task wrapper?

Expand the failed task in Android Studio Build Output and look immediately below the AAR metadata heading for the first numbered issue. If the IDE hides it, rerun the exact failing task shown in your build from the project root with more logging.

./gradlew :app:checkDebugAarMetadata --info # replace module/variant/task with the one from your own failure

If the task is :feature:checkReleaseAarMetadata, rerun that task instead. The goal is to expose the dependency requirement—not to generate the longest possible Gradle log.
