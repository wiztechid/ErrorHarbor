SignTool.exe Not Found: Find the Windows SDK Path First

If Windows says `SignTool.exe` is not found, first check the versioned Windows SDK folders under Windows Kits. If the executable exists, use its full path or a Developer shell; change PATH only when your build actually requires it.

Windows SDK · SignToolWindows 10/11 · Visual StudioLast reviewed Sep 26, 2026
🎯 You’re likely in the right place if:
A build, signing script or terminal says SignTool.exe cannot be found.You use Visual Studio, MSBuild, Windows SDK, WDK or a code-signing workflow.The failure occurs before the signing operation itself starts.
Choose the path that matches what you see
PowerShell finds one or more signtool.exe pathsUse the Developer shell or the exact SDK path; the tool is already installed.
No signtool.exe is found under Windows KitsInstall or repair the appropriate Windows SDK component.
Interactive shell finds it but the build does notThe build/CI environment has a different PATH or SDK discovery context.
Several SDK versions are installedMatch the SDK version your project/build requests. Then choose the SignTool architecture for the environment that runs it; x64 is the usual choice on a 64-bit Windows build machine, while x86 and Arm64 copies are also provided.
Difficulty: Easy–ModerateRisk: Low first
🔎 Fix #1 — locate the installed SDK copy

Use PowerShell to search the standard Windows SDK bin directory for installed SignTool versions.

Get-ChildItem "${env:ProgramFiles(x86)}\Windows Kits\10\bin" -Filter signtool.exe -Recurse -ErrorAction SilentlyContinue | Select-Object -First 5 -ExpandProperty FullName

Verify: If one or more full paths are returned, SignTool is installed. Copy one returned path and run it with /?. If that works, stop troubleshooting installation and focus only on how your shell, build, or CI resolves the SDK path.

More than one result? Do not simply use the first path. Check your project or build configuration for its Windows SDK version (for example, a WindowsTargetPlatformVersion/SDK setting). Prefer that matching version. Microsoft ships separate x86, x64, and arm64 SignTool paths; use the copy appropriate for the environment running the signing step.

Why this happens

Microsoft ships SignTool as part of the Windows SDK, typically inside a versioned `Windows Kits\10\bin\\` directory. A normal shell may not have that directory on PATH even though the tool is installed.

Diagnose before changing more

1
Does the SDK path contain SignTool?
If yes, use the exact path or a Visual Studio Developer shell before modifying global PATH.
2
Are you running a normal PowerShell/cmd window?
Developer Command Prompt or Developer PowerShell may provide the expected build-tool environment.
3
Is the Windows SDK component installed?
If the search returns nothing, verify the Windows SDK/Visual Studio workload rather than copying SignTool from another machine.

Fix #2 — use the Developer shell or the full SDK path

Run the signing step from Visual Studio Developer PowerShell/Command Prompt, or configure your build to use the full path returned by the search. This avoids a machine-wide PATH change.

& 'C:\Program Files (x86)\Windows Kits\10\bin\\x64\signtool.exe' /?
🟡 Before changing configuration: Replace the placeholder with the version and architecture that actually exist on your machine.

Verify: Run the exact discovered SignTool path with /?. The help output should open before you attempt signing.

Did Fix #2 work?

Fix #3 — install the Windows SDK component if SignTool is absent

If no SDK copy exists, install a Windows SDK that matches the version required by your project/build. If you use Visual Studio, open Visual Studio Installer → Modify and make sure a Windows SDK component for the required target version is installed; alternatively, use Microsoft’s official standalone Windows SDK installer. You do not need to download SignTool separately—it is installed under the SDK bin path.

signtool /?
🟡 Keep it reversible: Do not download a standalone SignTool.exe from unofficial DLL/tool sites.

Verify: After SDK installation/repair, rerun the location check and then signtool /? from the intended Developer shell.

Did Fix #3 work?

What not to do

Do not download SignTool.exe or Windows SDK DLLs from unofficial file-sharing sites.Do not add every Windows Kits version to the global PATH.Do not debug certificates or signing credentials until the SignTool executable itself can be launched.

Still seeing the error?

If the exact discovered signtool.exe path opens help successfully but your build still says it is missing, the executable is not the problem. Check the environment that launches the signing step.

1
Works by full path, fails as signtool?
Your current shell does not resolve the SDK bin directory. Prefer the Developer shell or configure the build with the exact discovered path.
2
Works interactively, fails only in MSBuild?
Inspect the MSBuild property, target, or script that supplies the signing-tool path instead of changing certificate settings.
3
Works locally, fails only in CI/CD?
Treat the runner as a separate machine. Confirm that its image contains the Windows SDK/SignTool and that the job can resolve the intended version and architecture.
Before escalating, capture:the exact build/terminal error textthe SignTool paths returned by the Windows Kits searchWindows SDK/Visual Studio versions installedwhether the failure is interactive, MSBuild, CI-only, or all threethe shell/build architecture if x86/x64 selection matters

Common error wording

“An error occurred while signing: SignTool.exe not found.” This wording usually points to the same missing-tool or SDK-discovery problem. Follow the Quick Check above first; do not disable signing or change certificates just to hide the error.
