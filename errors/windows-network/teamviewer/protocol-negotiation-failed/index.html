TeamViewer Protocol Negotiation Failed: Check Version and Network Path

This error appears after TeamViewer begins a connection but cannot complete session negotiation. There is no single universal cause, so start with version and network checks that are safe to verify.

TeamViewerWindows · macOS · Linux · Mobile clientsLast reviewed Sep 25, 2026
🎯 You’re likely in the right place if:
The remote side shows Protocol Negotiation Failed or Please try again.The connection begins but the remote-control session never opens.The issue may affect one endpoint, one network, or clients running different TeamViewer versions.
Choose the path that matches what you see
Many endpoints fail at the same timeCheck TeamViewer service status before changing local machines.
Only one endpoint failsUpdate/restart that endpoint and confirm its TeamViewer service is running.
Only one network failsFocus on proxy/firewall/outbound filtering rather than reinstalling TeamViewer.
Multiple networks fail with current clientsCollect logs/version/timestamp and escalate; avoid broad firewall disabling.
Difficulty: ModerateRisk: Low first
🔎 Quick Check — compare TeamViewer versions on both endpoints

Confirm both sides are running supported, current TeamViewer builds and restart the application/service before deeper network changes.

TeamViewer → Help / About TeamViewer → Version

Verify: Both endpoints show current supported versions and the TeamViewer service/application has been restarted.

Did updating or restarting clear the negotiation failure?

Before reinstalling: rule out a service outage

Open the TeamViewer status page and check whether Remote Connectivity or related services are degraded. If multiple devices started failing at the same time, this can save unnecessary local changes.

Why this happens

For this exact error, TeamViewer community staff have recommended updating affected clients, while TeamViewer’s current support documentation says the product initiates outbound connections and prefers TCP/UDP 5938, with TCP 443 as a fallback. That makes version parity and the outbound network path the safest first branches to test.

Diagnose before changing more

1
Does the failure happen only on one network?
If another network works, inspect proxy, firewall or outbound filtering on the failing network.
2
Are both endpoints current?
A version mismatch or outdated client is a low-cost condition to eliminate first.
3
Can TeamViewer reach its required outbound routes?
Corporate security tools can restrict outbound TeamViewer traffic even when general web browsing works.

Fix #2 — test the network path before changing the endpoint

Try the same connection from another network or temporarily bypass a corporate proxy path if policy allows. If the connection succeeds elsewhere, focus on outbound firewall/proxy rules rather than reinstalling the operating system.

🟡 Before changing configuration: Do not disable endpoint security broadly. Test with approved network changes and restore the previous policy after diagnosis.

Verify: Retry the same connection from the comparison network. If it works there, you have isolated the problem to the original network path.

Did Fix #2 work?

Fix #3 — allow the documented TeamViewer outbound ports and domains

In a managed network, configure the firewall or proxy according to TeamViewer’s official port guidance. Port 5938 is preferred; TCP 443 is used as a fallback when 5938 is unavailable.

Preferred: TCP/UDP 5938 Fallback: TCP 443
🟡 Keep it reversible: Apply network rules through your normal IT/security process instead of creating unrestricted outbound access.

Verify: Return to the original network and retry. TeamViewer should establish its outbound connection without requiring inbound firewall exposure.

Did Fix #3 work?

What not to do

Do not disable the firewall or endpoint security globally. TeamViewer documents outbound connectivity and does not require opening inbound ports for normal use.Do not whitelist a fixed list of TeamViewer IP addresses; TeamViewer says its server IP ranges change.Do not reinstall the operating system for a protocol-negotiation error before versions, service status and network path are ruled out.

Still seeing the error?

If versions match and the same failure occurs across multiple independent networks, capture the exact TeamViewer version, endpoint OS, timestamp and logs, then escalate to TeamViewer support. Avoid assuming a single community workaround applies to every negotiation failure.

Before escalating, capture:TeamViewer version on both endpointsoperating system on both endpointstimestamp/time zone of a failed attemptwhether another network succeedsrelevant TeamViewer logs with IDs or personal data redacted
